# CI-Sense benchmarks

This folder holds two benchmarks for one question: **when CI fails, does CI-Sense blame the right commit?**
They replace the 14 hand-made seed PRs in `seeds/` as the main evaluation. With 14 cases, even 14/14 only
shows that the true accuracy is probably above about 78%.

| Benchmark | Cases | Where the cases come from | Runs where |
|---|---|---|---|
| Synthetic | 140 | Generated by mutating a small library written for this benchmark | Locally, no GitHub needed |
| Real-repo | 17 | Real pull-request failures from open-source Python projects | Mined from GitHub, scored locally |

Both are scored by `scripts/bench_eval.py`. It feeds each case through the same functions the CI agent uses
(`distill_error`, then `score_candidate`, then the verdict in `agent/triage.py`) and compares three variants:

- **last_commit**: naive baseline that always blames the newest commit.
- **deterministic**: the agent's heuristic scoring only (its fallback when the LLM is unavailable).
- **llm**: scoring plus the Groq LLM verdict (`openai/gpt-oss-120b`, temperature 0). This is what runs in CI,
  without the Sourcegraph context.

Nothing is posted to GitHub.

## 1. Synthetic benchmark (140 cases)

### What is in it

- `fixture/`: a small retail library, `shop/`, with 5 modules (pricing, inventory, textutil, dates, stats)
  and 27 functions. Its test suite (`fixture/tests/`, 29 tests) is **deliberately incomplete**.
- `heldout/`: 26 extra edge-case tests that are not in the base suite.
- `cases.jsonl`: the 140 generated cases, one JSON object per line.

### How a case is made (`scripts/bench_generate.py`)

1. **Pick a bug.** The script tries every one-token edit in the library (`+`→`-`, `<`→`<=`, `and`→`or`,
   `10`→`11`, deleting a `not`) and runs the tests on each:
   - caught by the base tests: becomes a **logic_bug**
   - caught only by the held-out tests: becomes a **latent_bug**. The case adds a later, correct
     "add test" commit that exposes it, so the failing test is in a different commit from the bug.

   It also makes **test_bug** cases (a test's expected value changed while the code is fine), **rename**
   cases (a function renamed but the tests still use the old name) and **syntax** cases (a type-hint edit
   that drops the `:` on a `def` line).
2. **Build a real git history.** In a temporary repo it commits the clean library, then 1–5 commits:
   the bug plus **decoys**. Decoys are docstrings, comments, behaviour-preserving refactors, extra
   passing tests, README edits, valid dependency pins and new helper functions. About half of them target
   the same function as the bug, which makes them harder to rule out. Commit messages come from realistic
   templates such as "Tidy up subtotal".
3. **Record a real failure.** It runs `pytest -v` at the last commit and stores the actual output as the CI log.
4. **Check the ground truth.** A case is kept only if:
   - every commit before the bug passes,
   - the last commit fails,
   - `git revert` of the guilty commit alone makes the tests pass again,
   - for every category except latent_bug, the guilty commit is the first one that fails.

Generation uses a fixed random seed (7), so rerunning produces the same 140 cases.

### Mix

| By category | | By number of commits | |
|---|---|---|---|
| logic_bug | 61 | 1 | 19 |
| latent_bug | 25 | 2 | 40 |
| test_bug | 25 | 3 | 48 |
| rename | 15 | 4 | 20 |
| syntax | 14 | 5 | 13 |

Difficulty: 19 easy (one commit), 21 medium, 100 hard (a decoy touches the guilty function, or the case is
a latent bug).

## 2. Real-repo benchmark (17 cases)

### How cases are mined (`scripts/mine_real.py`)

For each repo, the script reads the last ~85 days of pull-request CI runs. GitHub deletes run logs after
about 90 days. It looks for a run that **failed** followed by a run that **passed** on the same PR branch.

- **Candidates:** every commit in the PR up to the failing run. This is the same set CI-Sense considers
  in PR mode.
- **Fix:** the 1–3 commits between the failing run and the next passing run.
- **Label (SZZ method):** take the lines the fix deleted or changed, and use `git blame` to find which PR
  commit wrote them. The case is kept only if all of those lines come from exactly one candidate. If the
  fix touches no candidate line, the failure was probably flaky, infrastructure or upstream, and the
  case is dropped.
- Also dropped: force-pushed history, PRs containing merge commits, and expired logs.

The failing job's real log is saved in `real_logs/` (gzipped). Cases are stored in `real_cases.jsonl`.

### Where they came from

9 repos were mined: pydantic, marshmallow, click, attrs, httpx, rich, textual, fastapi and pytest.
They yielded 113 fail-then-pass episodes, and 17 survived the filters. The other 7 repos on the default
list (aiohttp, scrapy, poetry, pip, sympy, flask, jinja) have not been mined yet. The main reasons
episodes were dropped: force-pushes (31), a fix that only added code so SZZ had nothing to blame (7),
and merge commits (4).

### Limitations of this set

- **13 of the 17 have only one candidate commit,** because projects run CI on every push. Any method gets
  those right. Only the **4 multi-commit cases** actually test attribution.
- **About 8 are lint, format, type-check or coverage failures** (fixes like "Auto format", "Fix mypy"),
  not failing tests.
- **The labels are automatic (SZZ) and have not been checked by hand.** SZZ is a standard research method,
  but it can be wrong.

## 3. Results (as of 2026-11-21)

The LLM runs are **incomplete**. Groq's free tier allows 200k tokens/day for this model, and each case uses
a few thousand tokens.

| Set | Cases | last_commit | deterministic | LLM |
|---|---|---|---|---|
| Synthetic, all | 140 | 44.3% [36–53%] | 58.6% [50–66%] | **100%** (126/126 run, CI 97–100%) |
| Synthetic, multi-commit | 121 | 35.5% | 52.1% | 100% (109/109 run) |
| Synthetic, latent_bug | 25 | 0% | 32% | 100% |
| Synthetic, hard | 100 | 27% | 48% | 100% (93/93 run) |
| Real, all | 17 | 82.4% (14/17) | 88.2% (15/17) | 4 run: 3 correct, 1 abstained |
| Real, multi-commit | 4 | 1/4 | 3/4 | 1 run: abstained |

Square brackets are Wilson 95% confidence intervals. Full breakdowns by category, difficulty and commit
count are in `results.json` (synthetic) and `real_results.json` (real).

### How to read these numbers

- **The LLM is far ahead of both baselines** on the synthetic set, especially where heuristics fail.
  On latent bugs, the failing test is in a different commit from the bug: 100% vs 32% for deterministic
  scoring and 0% for blaming the last commit.
- **100% on the synthetic set means it is too easy, not that CI-Sense is perfect.** Every bug there is a
  one-token change in a 150-line library, and the error usually points close to it. The same people wrote
  the library, the bugs and the decoys (author bias).
- **The real set is too small to give a reliable accuracy.** It shows that the pipeline runs end to end on
  real logs and real diffs. The one non-correct LLM verdict so far is a real multi-commit pydantic case,
  where it said no commit was responsible.
- Report the sets separately, with these caveats. Don't merge them into one headline number.

## 4. Reproduce or finish the runs

You need `GITHUB_TOKEN` and `GROQ_API_KEY` in the root `.env`. Use the Python environment from
`requirements.txt`.

    python scripts/bench_generate.py             # rebuild the 140 synthetic cases (about 10 min)
    python scripts/bench_eval.py                 # score synthetic -> bench/results.json
    python scripts/mine_real.py                  # mine real cases (slow; read-only on GitHub)
    python scripts/bench_eval.py --set real      # score real -> bench/real_results.json

LLM verdicts are cached in `runs.jsonl` and `real_runs.jsonl`. When Groq's limit is hit, the script waits
or stops, and **rerunning continues where it stopped**. To finish the missing verdicts, just rerun the two
`bench_eval.py` commands.
